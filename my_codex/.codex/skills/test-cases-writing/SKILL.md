# Составление сценарных тест-кейсов

Используй этот skill, когда нужно подготовить `.md` с ручными или будущими автотест-кейсами по функциональности MSG: эпик, задача, новая сущность, изменение существующей сущности, runtime-сценарий, UI/API-сценарий или сквозной бизнес-процесс.

Главная цель: тест-кейсы должны описывать поведение системы и проверяемые эффекты, а не только поля API-контракта.

## 1. Входной контекст

Перед написанием кейсов собери факты:

1. Прочитай инструкции:
   - корневой `AGENTS.md`;
   - `tasks/AGENTS.md`, если работа идет внутри задачи;
   - `TASK.md` и `TASK_MEMORY.md`, если они есть.
2. Найди все связанные Jira-задачи:
   - сам эпик;
   - задачи из Epic Link/parent/linkedIssues;
   - дефекты, которые блокируют или меняют ожидаемое поведение;
   - аналитические задачи, где может быть ссылка на Wiki.
3. Найди документацию:
   - OpenAPI/YAML в `msg-docs`;
   - Wiki-страницы, указанные в Jira;
   - Wiki-страницы по сущностям и API-эндпоинтам;
   - Wiki-страницы системных сценариев;
   - Wiki `MSG. Кэши WCS`, если функциональность влияет на WCS/runtime/cache.
4. Изучи уже существующие `.md`-кейсы в директории задачи, чтобы не дублировать и не противоречить им.

Если Jira/Wiki недоступны, не делай вид, что они проверены. Зафиксируй ограничение в файле и опирайся только на доступные локальные источники.

## 2. Обязательная проверка Wiki-сценариев

Для каждой затронутой сущности найди ее Wiki-страницу документации API и проверь нижний раздел `Сценарии запроса`.

Это обязательный источник, если задача:

- добавляет новую сущность;
- меняет существующую сущность;
- добавляет поля в существующий request/response;
- меняет сохранение, удаление, публикацию или runtime-использование данных.

В разделе `Сценарии запроса` выпиши:

- какие методы описаны: GET list, GET by id, POST, PUT, DELETE, action endpoints;
- какие таблицы затрагиваются;
- какие кэши затрагиваются;
- какие WCS/runtime-эффекты должны произойти;
- какие пункты помечены `TO_DO`, `TODO`, `-TO DO-` или похожей формулировкой.

Если сценарий помечен `TO_DO`, в тест-кейсе должна быть явная строка:

```markdown
**Недоработка документации:** ...
```

Не прячь `TO_DO` в общих рисках. Пометка должна стоять прямо в тех кейсах, которые должны отрабатывать этот сценарий.

## 3. Кэши WCS

Если задача затрагивает сущность, которая используется WCS/runtime, обязательно открой Wiki `MSG. Кэши WCS`.

Проверь, есть ли кэш для сущности:

- имя раздела в Wiki;
- кэш-сервис;
- имя кэша;
- ключ;
- формат значения;
- важные разделы XML/JSON.

Добавляй шаг проверки кэша в тест-кейс, если сценарий сохраняет, обновляет или удаляет данные, которые должны попасть в этот кэш.

Примеры:

- Сервис: кэш `Services`/`services`, ключ - имя сервиса.
- Привязка клиента к сервису: кэш `Service_partners`/`service_partners`, ключ - `<service name>_<partner_id>`.
- Шаблон: кэш `templates`, ключ - ID шаблона.

Если Wiki описывает сам кэш, но не описывает формат новых полей, все равно добавь cache-check, но не фиксируй неописанную структуру:

```markdown
Проверить значение в кэше `<cache name>` по ключу `<key>`.
```

Ожидаемый результат:

```markdown
В кэше `<cache name>` значение создано/обновлено; новые поля проверяются без строгой проверки структуры, так как их формат не описан в документации.
```

Не добавляй кэш-проверку в runtime-кейсы отправки автоматически. Сначала проверь Jira/Wiki: иногда runtime проверяет доступность через сервис или правило, а не напрямую через кэш.

## 4. Как отделять сценарные кейсы от контрактных

Контрактный кейс отвечает на вопрос: "Соответствует ли request/response схеме?"

Сценарный кейс отвечает на вопрос: "Что происходит с системой после действия?"

В сценарный кейс включай эффекты:

- сохранение в БД;
- обновление кэша;
- изменение доступности в UI/API;
- влияние на авторизацию или права;
- применение настройки в runtime;
- статусы сообщений и статистику;
- обратную совместимость старого сценария;
- негативные ветки и отсутствие частичного сохранения.

Не превращай сценарный файл в список endpoint-field проверок. Если нужно проверить только DTO ответа, это контрактный кейс.

## 5. Структура файла

Рекомендуемая структура `.md`:

```markdown
# <TASK>. Сценарные тест-кейсы

## Источники

## Результат сверки с Wiki

## Область сценариев

## Общие предусловия

## Сценарные тест-кейсы

### SC-001. Название

**Источник:** ...

**Недоработка документации:** ... // только если есть TO_DO или пробел постановки

**Предусловия:** ...

**Шаги:**

1. ...

**Ожидаемый результат:**

- ...

## Матрица приоритетов автоматизации

## Открытые вопросы перед автоматизацией
```

Нумеруй кейсы стабильно: `SC-001`, `SC-002`, ...

## 6. Что проверять для новой или измененной сущности

Минимальный набор сценариев:

- создание сущности;
- чтение списка;
- чтение карточки;
- обновление;
- удаление, если метод есть;
- негативный сценарий доступа или валидации;
- обратная совместимость старого сценария;
- сохранение в БД;
- обновление кэша, если сущность кэшируется;
- downstream/runtime-эффект, если сущность используется правилами, WCS, Broker API, LK, ACUI или статистикой.

Для новой сущности обязательно проверь:

- Wiki-страницу API-эндпоинтов этой сущности;
- раздел `Сценарии запроса`;
- OpenAPI в `msg-docs`;
- DB/Wiki-страницу таблиц, если есть;
- Wiki `MSG. Кэши WCS`;
- Jira-задачи реализации UI/API/DB/WCS/Rules/tests.

Для изменения существующей сущности дополнительно проверь:

- старые сценарии, которые не должны измениться;
- миграцию или дефолтные значения для старых данных;
- совместимость старых request body без новых полей;
- поведение при чтении старых записей.

## 7. TO_DO и недоработки документации

Если в Wiki есть `TO_DO`, тест-кейс не должен выглядеть полностью определенным.

Правильный стиль:

- "Проверять сохранение в API/БД/кэш можно";
- "WCS-эффект не считать полностью определенным до завершения постановки";
- "Не автоматизировать этот канал до уточнения сценария";
- "Ожидаемый HTTP/текст ошибки требует уточнения";
- "Формат новых полей в кэше не описан, проверяется только факт записи/обновления".

Неправильный стиль:

- молча включить `TO_DO`-поведение в ожидаемый результат;
- вынести все `TO_DO` только в общий раздел рисков;
- написать "документация не полная" без указания страницы, метода и затронутого кейса.

## 8. Сценарии по каналам

Если функциональность общая для каналов, не считай автоматически, что все каналы одинаковы.

Для каждого канала проверь:

- есть ли отдельная Wiki-страница;
- есть ли отдельный OpenAPI example/schema;
- есть ли применимый recipient или другая сущность, от которой зависит сценарий;
- есть ли исключения, например Email может быть явно исключен runtime-сценарием.

Если канал есть в API, но Wiki не описывает применимость бизнес-логики, пометь это как недоработку документации и не делай позитивный автотест до уточнения.

## 9. Матрица приоритетов

В конце файла добавь короткую матрицу:

- `P0`: основная цепочка настройки и бизнес-результата;
- `P1`: важные варианты, переопределения, редактирование, изоляция данных;
- `P2`: негативные ветки, диагностика, статистика, регрессия и кейсы с документационными ограничениями.

Приоритет не должен скрывать блокировку документацией. Если кейс P0 зависит от `TO_DO`, прямо укажи это в кейсе.

## 10. Финализация

После создания или обновления сценарного файла:

1. Проверь, что все источники перечислены с pageId/version или Jira key.
2. Проверь, что каждый найденный `TO_DO` отражен в конкретном кейсе.
3. Проверь, что кэшируемые сущности имеют шаг проверки кэша.
4. Обнови `TASK_MEMORY.md` с кратким итогом источников, найденных `TO_DO`, добавленных кейсов и открытых вопросов.
5. Не запускай build/compile и не делай commit/push, если пользователь этого не просил.
